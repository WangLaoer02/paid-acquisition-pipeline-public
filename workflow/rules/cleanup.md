> **paid-skit-cleanup v1.2.0**
> 清理 AI / Agent 过程残留、迁移脏数据和活动库中的重复历史记录，同时保护业务内容、正式 Skill、资产、关系和有审计价值的证据。
## 输入
- `scope`：workspace／page／database／subtree；只在用户授权范围内处理。
- `cleanup_mode`：conservative／strict；未指定时保守处理。strict 不扩大删除权限，不绕过保护项和 REVIEW。
- `target_patterns`：可选候选检索模式，不等于删除授权。
- `protected_fields`：可选附加保护字段，不得削弱内置业务、附件、关系和执行规则保护。
- `preserve_audit_history`：默认 true；保留有审计价值的历史。明确要求不保留也须核验范围和依赖，不自动删除业务事实或必要来源链。
## 触发
- 清理 AI 元信息、思考/执行残留、工具日志、迁移残留。
- 清理 Skill 库中的临时副本、重复 History、当前/历史混杂。
- 对页面、子树、数据库、Skill Library 或工作区做知识库卫生治理。
## 核心原则
**Search 只发现候选；Fetch 决定语义。最小安全修改后必须再次 Fetch。**
## 无损修改与指令派生
- “只输出成品”“前台简洁”“不要过程说明”约束交付展示，不授权删减 Skill 的实现、触发条件、角色映射、有效示例、参考库、异常处理、重试策略、授权边界或验收标准。文档更短、版本号更高不代表能力更完整。
- 修改前完整读取目标正文、必要依赖、当前指针与基线；遇到截断、未知块、无法访问的依赖或来源冲突，保留原内容并标 REVIEW，不从搜索摘要重建正文。
- 按最小语义单元记录“原条款 → 保留位置／等价条款／用户明确授权删除的依据”。清理目标之外的原文不重写；重复项只有在条件、例外、效果一致且目标可访问时才可合并，互补内容不算重复。
- 规则、例外、必要示例、引用、输入输出、数字阈值、失败恢复和权限约束逐项核对，未授权语义删除与未授权新增默认要求必须为零。只把全文缩成摘要、把方法示例换成原则、把可选改成必选，均不属于清理。
- 从用户请求派生维护指令时，区分用户原话、适用对象、允许的操作和 Agent 推导；推导不能扩大删除范围，不能把一次项目要求提升为全局规则。原始请求、派生指令与变更对照保存在独立审计记录，不写入业务执行正文，不保存私密思考过程。
- 修改前保存可回滚原文或精确逆向补丁。默认精确更新；不覆盖历史版本。移到参考文件的内容须在原执行路径提供明确、可访问的按需读取入口；移走不等于保留成功。
- 先核验新正文和依赖，再核验可下载 `SKILL.md`、本机／仓库入口与当前指针。正文、附件或指针不一致时，不宣称同步完成；保留旧件作为历史，不让未验收的新摘要自动接任 Canonical。
- 回归检查至少覆盖：清理“本轮自检通过”日志但保留自检标准；删除一次上传重试流水但保留失败恢复规则；隐藏角色映射的成品展示但保留生成公式与示例；精简主表但保留底层数据；默认输出仍允许用户明确要求的分析；源文件不完整时不写入。规则检查通过不冒充实际工具运行或作品质量通过。
## 分类
### REMOVE
- 最终正文中的 request/gen/provider ID、工具中转字段等纯执行元数据。
- 仅删除不承担业务、审计、恢复或复现用途的已结束执行流水，例如本轮自检结论、一次上传重试过程、临时预览说明。自检标准、上传/导入重试策略、fallback 规则、来源链与故障恢复办法必须保留；混合段落只删纯过程句。
- “本轮处理”“本次恢复”“字数统计”“自检结果”“为什么这样写”等 Agent 执行叙述。
- 数据库属性已经保存、正文再次重复且没有业务价值的元信息。
- 迁移时产生的临时/历史重复项：已经存在明确 Canonical 当前记录，且该副本不承担审计用途。
### PRESERVE
- 数据库业务属性、关系、日期、Files、图片和附件。
- 正式 Skill 合同与可执行规则。
- 用户原创分析/复盘，只要它本身属于业务内容。
- 事实来源、授权边界、决策相关 QA。
- SHA256、版本、文件尺寸、seed 等承担可复现或完整性用途的字段。
- 明确需要的审计/历史记录。
### REVIEW
- 可能同时是业务状态的 QA / Approved / Review。
- 可能承担审计价值的 History / Archive 页面。
- 仍可能被运行流程依赖的来源链或迁移说明。
无法确认时保留并列入 review。
## Workflow
1. 确定 scope，Fetch 目标页面/数据库 schema。
2. 涉及数据库或 Skill Library 时，先结构化查询当前/历史/重复记录。
3. 用多组高置信模式 Search 建立候选；不根据 Search snippet 直接删除。
4. 每个候选必须 Fetch。
5. 按 REMOVE / PRESERVE / REVIEW 分类。
6. 正文优先最小 `docs +update` 的精确 block 更新或 `sheets +cells-set` 的最小字段更新；纯脏副本优先移到指定归档区，不让它继续占活动库。只有工具支持且删除范围明确时才真正删除。
7. Skill Library 强制检查同一 Skill ID 的 Canonical：默认只能有一个 Active + 当前记录；历史版本不得继续占活动执行面。
8. 修改后逐页 Final Fetch；按修改前语义清单逐项核对保留项、依赖、附件和授权边界，执行适用的回归检查；数据库重新 query。写入成功或关键词消失不能单独判定无损。
9. 再做关键词扫描兜底。Search 索引若滞后，以当前 Fetch 为准。
10. 最终报告实际检查范围、已修复项、保留能力、回归结果、review、错误及未同步位置；详细原文与差异留在独立审计记录。没有完整基线时不宣称全量无损。
## Skill Library 专项规则
- 默认每个 Skill ID 只保留一个 Canonical 当前版本；明确支持并行 channel 的库除外。
- Canonical 当前行负责当前 URL / version。
- 迁移副本、临时副本、已淘汰 History 不留在活动执行面。
- History / Archive 不得伪装成当前入口。
- 清理一个 Skill family 时不顺手重写其他无关 Skill。
## Guardrails
- 不能仅因出现 `AI / analysis / ID / review / hash / source / metadata` 就判定为脏数据。
- 不连带删除 child page/database、schema、关系、资产或业务属性。
- 清理和文案优化分开；不借清理之名大范围改写正文。
- 模糊项保留。
## 验收
- [ ] 所有修改页完成 Final Fetch。
- [ ] 受影响数据库重新 Query。
- [ ] Canonical 当前记录完整。
- [ ] 图片/附件/关系/业务字段未受损。
- [ ] 当前正文中高置信过程残留消失。
- [ ] 本次目标中的重复/历史脏记录不再占活动库。
